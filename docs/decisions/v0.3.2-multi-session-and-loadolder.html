02 · 现在答不了的三个问题

每个问题都对应一个候选版本；拍板前先选“先回答哪个”。

1

切到超长会话再切回，究竟是谁在拖？

候选：后台 pane 仍在提交 / 隐藏 pane 的 DOM 仍参与布局 / 切回时重挂载与补页。当前 domPeak、mountedTurns 是整窗口径，无法区分会话；需要按 sid 的帧、提交、DOM、可见性。

最高
用户主观痛点
2

7.3 秒的 loadOlder 是首屏 hydrate，还是滚动补页？

候选：打开大会话时一次性补历史 / 滚动到顶部触发分页 / 宿主重试。当前只有次数与窗口 max，没有单次调用时间、页大小、触发来源；O3 补页合并是否值得做，取决于这个归因。

高
已有尖峰证据
3

输入卡顿到底是没复现，还是采样没覆盖？

这次 P95 12ms、max 13ms，说明“按键 → 下一帧”链路本身很干净。用户描述的“上下键不动”可能发生在超长会话或技能选择弹层，需要更长窗口与更细的 keydown → handler → commit → paint 分段。

中
本次未复现

04 · 推荐方案 A 的具体范围

只读、默认开、可单独关；不改变宿主任何方法返回值。

payload 新增 sessions

最多 5 个会话桶，按最近活跃排序：

sessions: [{
  sid, visible, lastActive,
  frames, commitRate,
  mountedTurns, dom,
  scrollP95
}]
  • 隐藏 pane 也记录，但 visible=false 单独标记
  • 不读消息正文，只读宿主已有的 DOM 计数与投影序号
  • 无会话时返回 []，schema 稳定

payload 新增 loadOlderDetail

最近 10 次调用的轻量记录：

loadOlderDetail: [{
  t, ms, ok,
  rowsBefore, rowsAfter,
  trigger // scroll | initial | unknown
}]
  • 不记录分页内容、不记录消息 id 列表
  • 只在 scrollDiagOn 开启时采集
  • 报告新增“Top 慢补页”与“触发来源”两行

状态、开关与清理

项规则验收
多会话归因新增 sessionDiagOn，默认 true；观测页一行开关关闭后 sessions 为 null，不遍历 pane
按 sid 桶observer 内存，最多 5 个；切会话只换桶，不写 store三段切换后每个 sid 的数字独立
__lagfixOff / 自禁用清空桶、移除监听、断开观察器sessions 为 null，无残留定时器
采样频率复用现有采集周期；DOM 计数沿用 60s 降频，不新增全树遍历不新增额外长任务；大会话下沿用现有降频
只读不读消息正文、工具参数、db.sqlite；只记 sid 与计数日志抽查无正文
