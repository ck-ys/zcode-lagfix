02 · 这轮要收的四类数据

同一台机器、同一批长会话、同一段操作路径；每类至少 3 轮，再看中位数。

场景怎么操作重点看什么用来判断
A 多会话切换 准备 3–5 个长会话，在会话之间来回切换 10 次以上；每次停 2–3 秒再切下一个。 pane.switches、switchP95/max、refocus.p95/max、sessions[].dom/commitRate、longTasks。 切换卡顿主要来自当前会话重绘，还是隐藏会话仍在工作（O7 的门槛）。
B 面板常开 打开右侧面板停留 60 秒，期间滚动聊天区、打开一个预览 HTML，再关闭面板。 pane.open、guardHits、frameP95、longTasks、dom、sessions[].dom。 面板常开期的卡顿是否与预览 HTML 自身绘制相关，还是聊天区 DOM 太大（O4 的门槛）。
C 长历史上翻 在超长会话里快速向上滚到很早的历史，连续触发多页补拉；再滚回底部。 scroll.p95、loadOlderCalls、loadOlderP95/max、mountedTurns、domPeak、顶部空白时间。 补页次数 / 单页耗时是否值得做 O3；顶部空白和 DOM 峰值是否值得做 O4。
D 回前台 Alt-Tab 离开 10 秒、60 秒、5 分钟各一次，再切回 ZCode；每次回来停 3 秒。 refocus.hiddenMs、refocus.p95/max、flushes、guardHits、longTasks。 P3 的 700ms 保护是否够；回前台卡顿是否来自宿主首帧重绘，插件还能不能帮上忙。
!

记录设置快照。至少记下 P1/P2/P3 是开还是关、采集间隔、是否开了多会话统计。没有设置快照的样本，不能拿来做 A/B。能接受的话，每类场景各跑一轮“三段全开”和“对应开关关闭”，否则只做归因，不声称改善。

03 · 四个候选，先看门槛

不是“能做就做”；每项都要有数据门槛、可还原开关和明确代价。

O4 · turn 内 content-visibility

优先候选默认关闭实验

只给 turn 内部的行级块加 content-visibility:auto，不动被 virtualizer 测高的 turn wrapper。目标是减少超长 turn 的布局 / 绘制成本。

  • 可能改善：长历史上翻、面板常开、回前台首帧。
  • 风险：锚点漂移、搜索/选中、预览内容高度、宿主测高。
  • 数据门槛：dom > 4000 或 3 秒内 longTasks > 6，且 A/B 后滚动 P95 或长任务下降 ≥20%。

O3 · 补页合并

优先候选默认关闭实验

快速上翻时把短时间内的多次 loadOlder 合并成一次，保留最后一页和滚动锚点；不伪造数据、不改消息顺序。

  • 可能改善：补页次数、单页耗时、顶部空白。
  • 风险：锚点、分页顺序、宿主重试、not-enough-queries 终态。
  • 数据门槛：3 秒内 loadOlderCalls ≥3 或 loadOlderP95 > 200ms，且顶部空白 >300ms。

O7 · 多会话调度

高风险管理先只归因

隐藏 pane 仍可能挂载并继续工作。插件只能在宿主允许的范围内减少通知 / 观测，不能安全卸载宿主内容。

  • 可能改善：多会话切换、隐藏会话的资源占用。
  • 风险：隐藏内容、切回时重新挂载、宿主生命周期；必须用户明确同意。
  • 数据门槛：sessions[].dom 或 commitRate 在非当前会话持续偏高，且 switchP95 > 120ms。

预览 HTML 自身绘制

大概率不做证据不足

预览内容的绘制发生在宿主 / 预览自身，插件没有安全的暂停接口。除非数据明确指向它，否则不碰。

  • 可能改善：面板常开时的持续卡顿。
  • 风险：暂停预览会改变用户看到的内容，属于“隐藏内容”范畴。
  • 数据门槛：面板常开 + 预览可见时 longTasks 明显高于预览关闭，且排除聊天区 DOM 因素。

04 · 推荐路线（暂定）

数据没回来前只定顺序，不锁定实现；每项都要能一键关回 v0.3.3。

先做 O4，再做 O3

两项都在 turn 内部或补页时序上，能本地开关、默认关闭、A/B 可回滚，且不改变消息数据。O4 先看 DOM/长任务，O3 再看补页次数/顶部空白；两项都达不到门槛就只保留观测。

O7 与预览只做归因

除非数据明确显示隐藏 pane 或预览绘制是主因，否则 v0.3.4 不卸载 pane、不暂停预览、不隐藏内容。要动这两项，必须先单独拍板。

✓

拍板规则：最多选 2 项；每项默认关闭；A/B 改善 ≥20% 或长任务下降 ≥30% 才保留默认路径；否则删掉或永久保持关闭。任何一项都不能改消息、会话、工具结果，也不能把“隐藏内容”当优化。

07 · 深度复核（读 ZCode v3.17.2 源码）

用本地源码仓（D:\Git\git-github\ZCode）核对 O3/O4 的机制是否成立，结论：方向对，但 O3 要改定义。

一次 loadOlder 的真实成本结构

后端 getRowsRange 每次先全量过滤整个投影再 .filter().slice(-60)，O(全会话行数)/次；前端 mergeOlderRows 整窗拷贝 [...older, ...window]；rowsPartitions WeakMap 按数组身份缓存，每次补页必失效重算。最后两次 setState 同步通知订阅者。

O3「合并」改定义为「触发降频」

宿主自己就有 loadingOlder 单飞防重入，不存在并发可合并；页大小 60 行是协议定的，插件改不了。可做的是大窗口时给触发限流（比如窗口 >3000 行时两次触发至少隔几百毫秒），减少 O(n) 全窗操作次数。注意：时间线触发是 fire-and-forget、锚点在触发时捕获，降频间隔太长锚点会陈旧。

O4 有宿主先例，可行

ConversationShareReadonlyTimeline 已对元素用 content-visibility:auto + contain-intrinsic-size:0 420px。活时间线只能加在 turn 内部行级块（virtualizer 要测 wrapper 高度），这个约束与 v0.3.1 拍板一致。

新增 P0：LoAF 脚本归因

记录 long-animation-frame 的 scripts[]（sourceURL / invoker / duration），确认 2.2 秒到底在后端 filter、前端整窗拷贝、还是同步订阅者里。先归因再动手，避免做错方向。只读，不碰数据。

✓

复核结论：O3+O4 方向仍然正确，但 v0.3.4 最终形态 = P0 LoAF 归因 + O3 触发降频（非合并）+ O4 turn 内 content-visibility。后端全量 filter 是宿主侧成本，插件只能减少触发次数、不能降低单次成本——这部分如实写进边界，不包装成插件已解决。
