下一项优化 先解开「定时器」归因歧义

v0.3.4 上线后，18:50–22:25 共 4273 条样本出现了两条不同的卡顿路径。其中 22:12–22:22 这条：长帧中位 118ms、约 2 次/秒、DOM 只有 1.2k，脚本归属全部是 TimerHandler——但本插件的节流补发同样用 setTimeout，现在无法区分「宿主定时器」和「我们自己的补发」。v0.3.5 先补上下文归因，再上唯一一项低风险实验。

P0 只读、默认开，用来判定长帧到底由谁触发；O5 作为唯一实验、默认关，只改通知时机。O6 与上游建议不在本版动手。

基于 v0.3.4（2026-11-11 已发布）· 本页只定路线

01 · 已确认的事实

只写日志与源码能证明的事；结论以样本数和时间窗标注。

存在两条卡顿路径

A 大 DOM 上翻：19:13:20–19:14:29，frameP95 152→588ms、scrollP95 212→861ms、DOM 3952→8678、补页累计 430→487 次。这正是 O3/O4 的目标场景。

B 小 DOM 定时器长帧

22:11–22:22：254 个 ≥100ms 长帧，中位 118ms、P90 141ms、最大 302ms；95% 与滚动事件共现，但 DOM 只有 ~1200，且侧栏全程关闭（254/254）。

这批长帧不是补页造成的

254 个长帧里只有 2 个落在 loadOlder 前后 2 秒内（中位距离 231 秒）。O3 降频对路径 B 基本不生效，不能把 B 说成 O3 已解决。

强制布局真实存在，但不是主因

246 帧里 198 帧 styleMs > 0，中位 22ms；脚本耗时最高单帧 114ms。布局是成本的一部分，剩下主要是脚本。

两项实验已开但还没数据

settings.json 显示三个开关均为 true；pace.allowed/skipped = 0/0，说明开启后还没有「滚动触发 + 窗口 >3000 行」的补页被计数。A/B 仍需按场景补。

空闲态是正常的

22:25 的样本 frameP95 18–61ms、eff=120、DOM 3571；长帧只在活动期出现，不是一直卡。

!

路径 A 与 B 要分开优化。A 是 DOM/补页成本（O3/O4 已针对，等 A/B 结论）；B 是「渲染频率 / 渲染成本」，现有开关都没有直接作用在它上面。

02 · 关键疑点：TimerHandler 不等于宿主定时器

这是必须先补归因的原因；不解决它，下一步优化只能靠猜。

我们自己的节流补发就是 setTimeout

makeThrottledSubscribe 在窗口未到期时用 setTimeout(fire, wait) 合并通知；fire() 里同步调用 React 的订阅回调，整段渲染都会被 LoAF 归到 TimerHandler:setTimeout。也就是说：现在看到的「定时器长帧」可能就是我们自己延迟掉的渲染。

宿主也有整树定时器

ConversationTimeline.tsx:721 在有运行中回合时每 1000ms setLiveNowMs(Date.now())，liveNowMs 是时间线顶层 state；ConversationTimeline.tsx:1353 还有一个内容宽度 settle 的 setTimeout。两者都会重新渲染时间线。

宿主脚本 URL 全空

实机 449 条脚本条目 sourceURL 全为空，只能看到 invoker。已在上一个提交把报告展示名回退到调用点（文件名 → 调用点 → ?），但「是哪个函数」仍然拿不到。

因此需要「时间上下文」

不 patch 宿主、不开 CDP 的前提下，最可靠的办法是记录长帧开始时距离上次通知、上次节流补发、上次滚动、上次投影提交各多少毫秒，再按最近者分类。

03 · 候选方案

全部遵守同一约束：独立开关、默认值有理由、关闭即回到 v0.3.4 行为、不读会话内容。

P0 长帧上下文归因：每条 ≥100ms 长帧记录 sinceNotify / sinceFlush / sinceScroll / sinceCommit，并给出分类 flush / notify / scroll / unknown；报告新增分类计数。 lafCtxOn
默认开（只读）		 每帧多 4 个整数、4 个模块级时间戳；不新增监听器、不改宿主、不改样本既有字段语义。 ≥90% 长帧能归入四类之一；unknown <20%；关闭后 laf 恢复 v0.3.4 形状。
O5 滚动期通知合并加严：滚动进行中把通知窗口下限抬到 250ms；停止滚动 400ms 后回到用户设定（含自适应下限）。只影响通知时机。 scrollMergeOn
默认关（实验）		 滚动中内容更新最多晚 250ms；不动数据、不动补页、不改 store；关掉立即恢复。 同场景 A/B：scrollP95 或长任务数下降 ≥20%（长任务下降 ≥30% 亦可），顶部空白时间不变差，滚动中仍持续有提交。
O6 隐藏 pane 的 store 通知降频：按 store 实例识别所属 pane，不可见时把窗口抬到 500ms 或暂停。 待定

U1 上游建议（只写文档，不改宿主）：把运行中 1 秒时钟收敛到局部组件；把 syncMessageLayerMask 移出滚动同步路径。 —

为什么 O5 而不是 O6：O5 只改我们已有的节流窗口，失败可立即回退；O6 需要猜 store 与 pane 的对应关系，一旦映射错会把可见会话也降频。先做低风险、可度量的那一个。

04 · 推荐路线

一个只读归因 + 一个实验，不允许再加第三项。

顺序

先实现 P0 并收集一轮数据（1–2 天）；用 /lagfix report 的分类计数确认长帧主体。O5 与 P0 同版发布，但默认关，等你按 A/B 场景手动开启。

不做什么

不 patch 宿主定时器与 React、不注入 CDP、不折叠或隐藏消息、不改 loadOlder 返回值（O3 已定稿）、不把 O6 塞进本版、不因为「感觉更快」就宣布改善。

数据口径

P0 的 since* 用 performance.now() 与 LoAF entry.startTime 对齐；时间戳只在内存环形缓冲，随样本上报毫秒差，不落原始时间序列。

回退路径

P0 关闭 → laf.detail 恢复 v0.3.4 字段；O5 关闭 → 通知窗口回到 120ms / 自适应 / 面板常开 / 回前台 现有规则；__lagfixOff()、自禁用、暂停三条路径都要清掉新时间戳与开关。

05 · 验收场景

同一台机器、同一批会话；每项至少 2 轮，先看中位数再看极值。

场景怎么操作重点看什么用来判断
P0 归因 正常使用 10 分钟以上，覆盖：空闲、流式输出、快速上翻、面板开关。 报告里 flush / notify / scroll / unknown 四类计数与占比。 长帧主体是「我们延迟的渲染」「直通通知」「滚动处理」还是「宿主定时器」。
O5 A/B 同一超长会话、同一段历史、同样速度上翻 3 次：O5 关 → 开 → 关。 scrollP95、frameP95、长任务数、顶部空白时间、滚动中 frames 是否持续。 是否过 ≥20% 门槛；不过就永久默认关并如实标注。
O3/O4 补测 按 v0.3.4 发布说明的 A/B 步骤各做一轮。 pace.allowed/skipped、DOM 峰值、锚点漂移、首 turn header 是否出现。 两项实验是保留、调参，还是永久默认关。
