NEXT RELEASE · v0.3.5 · 深度评估版

最佳推荐 P0 归因 + O5 面板期合并 + U1 上游文档

三轮实机对照（无负载 / 9 个子智能体隐性运行 / 4 个 pane 可见 / 面板快速滑动）已经把成本来源分开：子智能体计算不占渲染主线程，显示它们的 pane 才占；滑动是最贵的动作。插件唯一能调的变量是「通知合并」，所以 v0.3.5 只做这一项实验，并把归因做准。

证据 3 轮 × 9 并行任务 样本 带长帧归因 500+ 条 推荐 A：P0 + O5 + U1 边界 不承诺修好 webview
一句话选择：先做 P0，再让 O5 试跑

P0 只读、零风险，决定后续所有判断；O5 只改通知时机，默认关，过不了 20% 门槛就永久关掉。O3b 与 O6 都不进本版。

基于 v0.3.4（2026-11-11 已发布）· 本页只定路线
✓ 最佳推荐 · 方案 A 风险 低 工时 小 可回退 是

v0.3.5 = P0 归因补强（默认开）+ O5 面板期合并（实验、默认关）+ U1 上游文档

理由只有一条：这是唯一一组「能立刻做、不碰宿主、还能为下一步提供证据」的组合。O3b 会碰首 turn 完整性，O6 需要猜 store→pane 映射，两者都该等 P0 数据。

P0 · 默认开给每条 ≥100ms 长帧标出触发来源与面板状态，回答「谁在占主线程」。
O5 · 默认关面板打开时通知窗口 300→400ms、角标 1.8s→3s；只改时序，失败即关。
U1 · 只出文档把 webview 合成证据交给上游；插件改不了那条链路，就不假装能改。

04 · 修复前：成本怎么叠起来的

三条支线共用一个主线程；插件当前只参与节流与观测。

① 主会话运行/回复投影提交约 4 次/秒；大 DOM 会话最高 9.9k 节点
↓
② store 通知 → 插件节流窗口 120ms / 自适应 200–300ms / 面板常开 300ms；到期用 setTimeout 补发
↓
③ 主时间线渲染每条通知一次渲染，9.9k DOM 下单次 100ms+
③′ 每个可见子智能体 pane 渲染C 段实测：4 个 pane 流式输出 → 长任务峰值 41
↓
④ 宿主布局效应遮罩同步（6 次样式写 + 几何读）、虚拟化测高、滚动补偿
↓
⑤ 主线程排队 ← 面板 webview 滚动/合成D 段实测：滑动时 frameP95 236ms、长任务 62 次/3 秒
↓
⑥ 长帧 100–1500ms → 面板滑动掉帧

注：子智能体本身的推理在 agent 运行时里，不进渲染主线程（B 段证明）；进主线程的是「把它们的输出画出来」。

05 · 修复后：推荐方案怎么改

只加两个开关与一段文档；宿主渲染链路一行不改。

① 主会话 / 子智能体运行（不变）插件仍只合并通知，不改数据、不改宿主
↓
② P0 归因层（默认开，只读）每条长帧记录距上次通知/补发/滚动/提交的毫秒数；分类 flush / notify / scroll / other；样本带 paneOpen / panelQuiet
↓
③ O5 面板期合并（实验，默认关）面板打开：通知窗口 300→400ms、角标 1.8s→3s；面板关闭立即恢复
↓
④ 可见 pane 与主时间线的渲染次数下降每次渲染成本不变，只是次数变少；预期 -20%~-30%，需 A/B
↓
⑤ 主线程给面板 webview 合成让出时间插件唯一能影响到那条链路的点
↓
⑥ 用 P0 数据判定是否过线长帧数或 frameP95 下降 ≥20% → 保留可选；否则永久默认关并如实标注
