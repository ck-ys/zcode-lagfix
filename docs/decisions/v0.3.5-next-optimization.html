NEXT RELEASE · v0.3.5 · 最佳推荐方案

先量准，再让路 面板滑动卡顿的可行边界

你复现的路径：长会话运行/回复中 + 右侧面板打开 HTML + 在面板里高频上下滑动。日志里这段时间聊天区零滚动、零提交，主线程仍持续每秒产生 3–10 个 100ms+ 长帧。根因一半在宿主 <webview> 合成，插件改不了；插件能做的是把归因做准，并在面板期给主线程让路。本页给出唯一推荐方案与修复前后流程。

状态 设计完成 · 待拍板 证据 496 条长帧样本 / 22:11–22:35 推荐 P0 + O5 + U1 不承诺 修好 webview 绘制
v0.3.5：归因（默认开）+ 面板期合并（实验，默认关）

P0 只读、无行为改动；O5 只改通知时机，关掉即回到 v0.3.4。O3b 自动补拉降频后置——它解决的是另一条路径，且动它会碰首 turn 完整性。

基于 v0.3.4（2026-11-11 已发布）· 本页只定路线

01 · 为什么是这三项（结论先行）

一句话：能改的只有「通知合并」和「归因」；补页降频与 webview 合成都不在本版。

候选针对哪条路径证据本版决定理由
P0 归因补强 全部长帧 现在 TimerHandler 同时可能是插件补发、宿主 1s 时钟、面板 webview 相关定时器，无法区分 做，默认开 只读、零行为改动；不做它，后面所有缓解都是猜。
O5 面板期合并 面板 HTML 滑动 面板期零滚动零提交仍有 20–33 个长帧/3 秒；插件唯一可控变量是通知频率 做，实验默认关 300→400ms 只让时间线少渲染几次，给 webview 合成让出主线程；风险为零，但收益需 A/B。
U1 上游文档 面板 HTML 滑动 UnifiedBrowserView.tsx:41：webview guest 在宿主 DOM 内合成，滚动绘制成本落在宿主渲染层 做，只出文档 插件没有 API 能改 webview 合成；把证据交上游是唯一正确动作。
O3b 自动补拉降频 长会话上翻 40 秒 +78 次补页、P95 561ms、最长 1517ms；但 O3 只覆盖 4/200 后置 跳过 effect 自动补拉会让首 turn header 延迟；先等 P0 证明面板期长帧与补页相关。

02 · 修复前：现在卡在哪

两条路径共用一个主线程；插件当前的参与点只有节流与观测。

路径 A · 面板 HTML 高频滑动

① 长会话运行/回复投影提交约 4 次/秒（commitP50 ≈ 240ms），大 DOM 会话最高 9.9k 节点
↓
② store 通知 → 插件节流窗口120ms / 自适应 200–300ms / 面板常开 300ms；窗口未到期时用 setTimeout(fire) 合并补发
↓
③ React 渲染时间线每条通知触发一次时间线渲染；9.9k DOM 下单次渲染可达 100ms+
↓
④ 宿主布局效应消息层遮罩同步（6 次样式写 + 几何读）、虚拟化测高、滚动补偿
↓
⑤ 主线程排队③④ 与右侧面板 webview 的滚动/合成争同一个主线程
↓
⑥ 右侧面板 <webview> 滚动/合成guest 像素在宿主 DOM 内合成，滚动时持续产生合成/绘制工作
↓
⑦ 长帧 100–1500ms → 面板滑动掉帧实测：零滚动零提交时每 3 秒仍有 20–33 个 ≥100ms 长帧，中位 139ms

实测补充：这段里 turnContentVisOn（屏外减负）是开着的，长帧仍为 139ms 中位——它只省屏外绘制，救不了屏内与 webview 合成。

路径 B · 长会话上翻补页

滚动到接近顶部handleScroll 同步调用 onLoadOlder()
SessionPane effect 自动补齐首 turn 缺 header 时触发，cursor 去重，跳过不会重试
↓
插件 O3 降频判定只拦「滚动派发栈内」的调用：实机约 200 次里只命中 4 次；effect 自动补齐按设计不拦
↓
后端全量过滤 + 前端整窗拷贝每次 O(全会话行数)；实测单次 P95 561ms、最长 1517ms，40 秒内 78 次
↓
DOM 3k → 9.9k，frameP95 12 → 158ms补页与渲染叠加，进入下一轮长帧

03 · 修复后：推荐方案怎么改

只加两个开关与一段文档；宿主渲染链路一行不改。

① 长会话运行/回复（不变）插件仍然只合并通知，不改数据、不改宿主
↓
② P0 归因层（默认开，只读）每条 ≥100ms 长帧记录：距上次通知 / 上次节流补发 / 上次时间线滚动 / 上次投影提交的毫秒数；分类 flush / notify / scroll / other；样本带 paneOpen 与 panelQuiet（面板开着且聊天区没滚）
↓
③ O5 面板期合并（实验，默认关）检测到面板打开：通知窗口下限 300 → 400ms；角标定位 1.8s → 3s；面板关闭立即恢复
↓
④ 时间线渲染次数下降预期 -20%~-30%（需 A/B 证实）；每次渲染的耗时不变，只是次数变少
↓
⑤ 主线程给面板 webview 合成让出时间这是插件唯一能影响到那条链路的点；不能消除 webview 自身绘制成本
↓
⑥ 用 P0 数据判定是否过线长帧数或 frameP95 下降 ≥20% → 保留可选；否则永久默认关，并如实标注「未达门槛」
!

不承诺：面板 HTML 自身的滚动绘制、webview 合成、宿主 1 秒 liveNowMs 整树时钟，这三项插件都改不了。O5 只减少「时间线渲染」这一份竞争成本，可能只占面板期长帧的一部分。

04 · 归因 → 决策映射（拿到 P0 数据后怎么走）

这张表是 v0.3.5 之后的分叉条件，先写清楚，避免下次又靠感觉。

P0 分类结果说明下一步
flush 占比最高长帧紧跟在本插件节流补发之后O5 继续加严（400→500ms）或按面板期暂停通知；A/B 验证。
notify 占比最高通知未合并、直接触发渲染降低基础窗口或按 DOM 规模自适应，先量再调。
scroll 占比最高滚动事件处理本身重O3b 自动补拉降频 + 遮罩同步抑制复查。
other 占比最高宿主定时器、webview 合成或纯绘制停插件侧优化，集中出 U1 上游证据；不在插件里硬扛。

05 · 验收：你怎么用三段对照验证

同一个长会话保持回复中，右侧面板打开同一个 HTML，每段 30 秒。

段操作看什么说明什么
1面板关闭，不操作laf.count、frameP95大 DOM 会话底噪
2面板打开，不滚动同上 + paneOpen/panelQuiet面板内容自身绘制
3面板打开，快速上下滑同上 + 主观跟手度webview 滚动/合成成本
4第 3 段重复，O5 开/关各一轮长帧数、frameP95、longTasksO5 是否过 20% 门槛

判定门槛沿用 v0.3.4 实验规则：长帧数或滚动 P95 下降 ≥20%（或长任务下降 ≥30%）才保留；否则默认关并如实标注。
