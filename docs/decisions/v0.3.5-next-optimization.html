下一项优化 先分清「谁在占主线程」

01 · 已确认的事实

只写日志与源码能证明的事；结论标注样本数与时间窗。

面板期长帧：最硬的一组数据

22:33:02–22:33:41：时间线滚动 0 次、投影提交 0 次，仍出现每 3 秒 20–33 个 ≥100ms 长帧（中位 139ms、P90 345ms、最大 1501ms），强制布局中位 65ms。侧栏此时 722px 打开。

面板期在日志里的占比

带长帧归因的 496 条样本中，面板打开 115 条；其中 70 条「无时间线滚动」。这 70 条里有 17 条长帧数 ≥10，全部集中在 22:30–22:39（中位 16.5、最大 33）。

长会话滚动本身也很重

22:32:29–22:32:56：40 秒内补页 +78 次，单次 P95 561ms、最长 1517ms；frameP95 从 12 升到 158ms；DOM 3k→9.9k。

O3 降频基本没覆盖到

约 200 次补页里，只有 4 次落在 scroll 派发栈内（pace.allowed/skipped = 4/0）。绝大多数补页来自 SessionPane.tsx:4870 的 effect 自动补齐，O3 按设计不拦它。

O4 开着也压不住屏内成本

面板期这段 turnContentVisOn=true（data-lagfix-cv 生效），长帧中位仍 139ms。它只省屏外绘制，对屏内内容与 webview 合成无效。

宿主面板是 webview

UnifiedBrowserView.tsx:41：网页像素由 renderer 内的 <webview> guest 直接渲染、在 DOM 内合成。也就是说面板 HTML 的滚动绘制成本落在宿主合成层上，插件没有任何 API 能改它。

!

这条路径的瓶颈很可能不在插件管辖范围内。插件能做的只有：把归因做准（谁触发、面板期还是聊天期），以及在面板交互期降低我们自己和宿主通知链路的竞争成本。面板 webview 的绘制开销不能包装成「已优化」。

02 · 两个必须先解开的歧义

不解决它们，任何缓解都只能靠猜。

歧义一：TimerHandler ≠ 宿主定时器

本插件节流补发就是 setTimeout(fire, wait)，fire() 里同步跑 React 订阅回调，整段渲染都会被 LoAF 记成 TimerHandler:setTimeout。宿主还有 ConversationTimeline.tsx:721 的 1 秒 liveNowMs 整树时钟。现在无法区分这三者。

歧义二：面板滚动我们看不见

插件的滚动计数只认 [data-v4-timeline-scroll] 和会话 pane；webview 内部的滚动事件不会冒泡到宿主文档。所以「面板在滑」在样本里表现为「滚动 0、提交 0」——和你实际的操作对不上。

解决方式：时间上下文 + 面板标记

长帧开始时记下距「上次通知 / 上次节流补发 / 上次时间线滚动 / 上次投影提交」的毫秒数，按最近者分类；样本额外记 paneOpen 与「面板打开且无时间线滚动」的 panelQuiet 标记。

边界：不能声称测到了 webview 内部

panelQuiet 只代表「面板开着且聊天区没滚」，不能证明 webview 正在滚。报告与文档必须按这个口径写，避免把相关性说成因果。

03 · 候选方案

全部遵守：独立开关、默认值有理由、关闭即回到 v0.3.4、不读会话内容。

编号做什么开关 / 默认代价与边界验收门槛
P0 长帧上下文：每条 ≥100ms 长帧记录 sinceNotify / sinceFlush / sinceScroll / sinceCommit，分类 flush / notify / scroll / other；样本加 paneOpen 与 panelQuiet；报告新增分类计数。 lafCtxOn
默认开（只读）		 每帧多 4 个整数；4 个模块级时间戳；不新增监听器、不改宿主。面板 webview 内部状态仍不可见。 ≥90% 长帧可归入四类；other <30%；关闭后 laf 恢复 v0.3.4 形状。
O5 面板期合并：paneOpen 时通知窗口下限从 300ms 抬到 400ms，角标定位降到每 3 秒一次；面板关闭立即恢复。 panelQuietOn
默认关（实验）		 面板开着时长会话内容更新最多晚 400ms；不碰 webview、不改布局；关掉即恢复。收益可能有限，必须先 A/B。 同场景（长会话运行 + 面板 HTML 快速滑动）A/B：长帧数或 scrollP95 下降 ≥20%；不过就永久默认关。
O3b 自动补拉降频：对 effect 自动补齐也做限流（同一会话 800ms 内只放行一次），并保留首 turn 完整性闸门。 待定

U1 上游建议（只写文档）：面板 HTML 预览的滚动绘制落在宿主合成层；建议改用独立 BrowserView/进程隔离，或限制预览页的动画与超大内容。 —

04 · 推荐路线与验收

一个只读归因 + 一个低风险实验，不加第三项。

发布内容

P0 默认开；O5 默认关；U1 只出文档。O3b 与「隐藏 pane 降频」留到拿到 P0 分类数据之后。

你的复现路径 A/B

同一长会话保持回复中，面板打开同一个 HTML：关 O5 快速滑 30 秒 → 开 O5 快速滑 30 秒 → 再关。对比长帧数、frameP95、强制布局时长与主观跟手度。

数据口径

P0 的 since* 用 performance.now() 与 LoAF entry.startTime 对齐；只在内存环形缓冲，样本上报毫秒差，不落原始时间序列、不含任何页面内容。

回退路径

P0 关闭 → laf.detail 恢复 v0.3.4 字段；O5 关闭 → 回到 P2 的 300ms 规则；__lagfixOff()、自禁用、暂停三条路径都清掉新时间戳与标记。

场景怎么操作重点看什么用来判断
A 面板 HTML 滑动 长会话保持运行/回复中，右侧面板打开一个 HTML，快速上下滑动 30 秒；O5 关/开各一轮。 laf.count、laf.detail[].since*、paneOpen/panelQuiet、frameP95、longTasks。 长帧是插件补发、宿主定时器、还是面板期其它来源；O5 是否过 20% 门槛。

C 静止对照 同样的长会话，面板关闭、不做任何操作 30 秒。 长帧计数与 frameP95。 区分「面板交互成本」与「大 DOM 底噪」。
