02 · v0.3.0 为什么没盖住

两个已有开关都只作用于“通知时机”和“一次性全量补拉”，不作用于滚动期间的 DOM 规模。

订阅通知节流

只把 store 的 listener 通知合并到每 120–300ms 一次。它不阻止 React 在滚动时因虚拟列表变化而重渲染，也不减少已挂载的节点数。

证据：fix.eff=300结果：P95 仍 166ms

大会话保护

只拦 loadAllOlder() 的一次性全量补拉；正常上翻的 loadOlder() 分页仍然放行。这次是连续滚动触发的分页与挂载，不在保护范围。

证据：bigApplied=true结果：big 拦截 10 次仍卡

自适应窗口

帧 P95 ≥150ms 时把窗口抬到至少 300ms。它已经生效，但一帧里的布局/绘制并不因为“晚 180ms 通知”而变便宜。

证据：eff 从 120 → 300结果：长任务反而更集中

03 · 根因假设与证据强度

“已证实”只指日志与源码能同时对上；其余标为待验证，不用模块名或时间接近归因。

H1

虚拟单元是“一整轮 turn”，单轮内部不虚拟化 高

ConversationTimeline.tsx 的 ROW_OVERSCAN=2，虚拟列表只按 turn 计数；一个超长 turn 里的用户行、assistant work、工具卡、历史 chunk 会随 turn wrapper 一起挂载。滚动到这种 turn 时，DOM 从 3k 跳到 9.2k，正好对应 166–213ms 帧与 20–33 个长任务。宿主注释也写明“虚拟单元是一整轮长正文”，过去前后各 8 轮会在搜索跳转时同步挂载大量屏外 Markdown，因此已把 overscan 降到 2；但单轮内部仍未分段。

高
源码 + 日志
H2

提前两个视口触发 loadOlder，滚动中连续前插 中–高

timelineScrollAnchor.ts 的预取阈值是 2 个视口；SessionPane.tsx 在接近顶部时自动 loadOlder()。连续滚动可能连续触发分页、merge 与 prepend 锚定；loadOlder 不改 snapshot.seq，现有 0.77/s 的提交计数看不到它。更关键的是，每次前插都会换掉 rows.window 的引用，而 conversationTurnRenderUnits.ts 的历史缓存以 cache.rows === rows 判等，引用一变就整段 history 重投影，再叠加虚拟列表计数增长。

中–高

H3

新挂载 turn 内的 Markdown / 代码高亮 / 表格 / 图片成本 中

同样一次挂载，纯文本与含大量代码块、表格、图片的 turn 成本可能差一个量级。当前日志没有“最长任务归因”，无法区分是 React 挂载、Markdown 解析、语法高亮还是图片解码。

H4

每个 scroll 都同步重写消息层遮罩 中

handleScroll 每次都调用 syncTurnNavigatorViewport → syncMessageLayerMask，同步写 6 个 mask 样式（maskImage / maskPosition / maskSize 各两套）并读取 3 个几何值；mask 作用在包含全部消息的整层上，可能迫使浏览器在滚动时重绘整层。它不改变 DOM，但正好是“每帧都跑”的放大器，需用 O2 的 A/B 开关验证。

还缺的一刀：当前 dom 字段每 60 秒才全量数一次，9,230 只是采样瞬间，真实峰值可能更高；也没有 loadOlder 次数、滚动事件数、最长任务归因。另有一处口径要修正：data-projection-seq 只反映 snapshot.seq，loadOlder 不递增 seq，所以不能用 0.77/s 排除补页。下一版应先补齐这四类字段，否则容易把 H2/H3 误判成 H1。

三路研究结论（DS Pro / DS Flash / GLM-5.3）

共同判断
  • 根因不在通知频率：seq 提交不到 1 次/秒，帧 P95 仍 166ms。
  • 最值得先验的是“每个 scroll 都写 6 个 mask 样式 + 读几何”和“整轮 turn 全量挂载”。
  • 先补滚动观测（尤其 scrollP95）再谈改行为。
  • 滚动期折叠/隐藏工具卡会改高度、藏内容，明确不做。
分歧
  • 补页：DS Pro/GLM 支持“首次直通 + 距顶远时合并后续”；DS Flash 反对延迟，认为会破坏触发瞬间的 prepend 锚点，主张把每页 60 行降到 30 行。
  • CSS 降载：DS Pro/GLM 认为可在 v0.3.1 灰度；DS Flash 主张先只验 mask，v0.4 再上行级 content-visibility。
拍板建议

v0.3.1 主交付只放 O1 观测 + O2 遮罩抑制；O3 补页合并、O4 CSS 降载另开分支、默认关，用同一套滚动脚本各测一轮。mask 若降不到 10%，说明它不是主因，再按数据决定 O3 还是 O4。

07 · 需要你拍板的三件事

这三项会直接改变实现范围；其余按推荐默认值即可。

1. 补页延迟可接受吗？

O3 只在“距顶 >1 视口且连续滚动”时合并后续补页，首次/近顶/搜索/分享都直通；另一派认为延迟会破坏锚点，主张把每页 60 行降到 30 行。你更接受哪种？

2. 要不要默认开 O4？

content-visibility 可能降 DOM 布局成本，也可能让滚动条高度抖动。建议默认关、实验开关；是否愿意在 v0.3.1 就带它？

3. 四项待办怎么排？

滚动、子智能体面板、多会话同时、频繁切换。建议顺序：滚动 → 频繁切换 → 多会话 → 子智能体；理由是与当前痛点和改动面匹配。
