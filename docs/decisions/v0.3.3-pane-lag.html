02 · 宿主源码里，开合到底做了什么

以下均在本机 ZCode 源码仓核对过；不是按记忆写的。

① 200ms 的 flex-grow 过渡

useAnimatedResizablePanel.ts 在显式展开/收起时给 panel 元素加 transition-[flex-grow] duration-200 ease-out，下一帧再调用 panel.resize() / panel.collapse()；transitionend 或 240ms 兜底后移除。也就是说，开合不是一次布局，而是连续 200ms 的中间尺寸。

② 会话列从 100% 收到 52%

WorkspaceShellLayout.tsx 的 conversation-column 在侧栏可见时默认 52%，侧栏 browser 默认 45%。会话列每一帧变窄，虚拟列表就要重新测量、重新排版；5.7k DOM 时这不是免费的。

③ 每帧都在读写消息层遮罩

ConversationTimeline.tsx 对滚动容器和消息层挂了 ResizeObserver，回调里 syncMessageLayerMask() 会读 clientHeight/scrollHeight/scrollTop/offsetTop，再写 6 个内联 mask 样式。开合动画期间尺寸每帧变化，这个回调就每帧跑一次。

④ 220ms 后才挂重内容

AnimatedSidePanePanel.tsx 的 PREVIEW_PANE_RESIZE_SETTLE_DELAY_MS = 220：窗口/面板尺寸停止抖动前，预览重内容先不渲染；侧栏宽度还要 ≥96px。也就是说，最难的那一下（HTML/Shadow DOM 挂载）大约落在开合动作的 220ms 之后，正好在 200ms 过渡结束附近。

⑤ 角标自己每帧强制布局

lagfix-observe.js 里 surfaceRO 观察 composer，回调直接调用 positionBadge()；positionBadge() 又会走 composerSurface()、elementsFromPoint() 和多次 getBoundingClientRect()。面板开合时 composer 每帧变宽/变窄，这个回调就每帧跑一次——在 5.7k DOM 上形成每帧强制布局。这是插件自己造成的，必须先在 420ms 保护窗口里 early-return。

⑥ 回前台同步补发所有通知

bgFlushers 在每个节流订阅里注册一个 flushOnVisible；visibilitychange 回前台时用一个 for 循环同步调用全部 flusher。React 19 每次 commit 会重新订阅，挂起的 flusher 可能不止一个；多个会话/订阅就会在同一拍触发多次 commit。注意 Alt-Tab 不一定触发 visibilitychange，还要用 window.focus/blur 兜住。

i

结论：一次“打开右侧面板”串起了六件事——200ms 的 flex 动画、会话列每帧重排、消息层每帧 mask 读写、220ms 后预览重内容挂载，以及插件自己的每帧角标强制布局；回前台则是第七条独立链路。v0.3.2 只记录这些，不干预；v0.3.3 要动的是其中可控的三段：开合 420ms、面板常开期、回前台 700ms。

04 · 推荐 A 的具体范围

先写 spec 和红基线测试，再动代码；每项都能单独关。

P0 · 侧栏 + 回前台归因（paneDiagOn，默认开）

只读，不改宿主。用宿主已有的两个标记定位：

frame = document.querySelector('[data-workspace-side-frame="true"]')
panel = frame.closest('[data-panel]')
open  = frame.getAttribute('aria-hidden') !== 'true'
  • 观察 frame 的 aria-hidden 与 panel 的 class；宿主显式开合会加 transition-[flex-grow]，这是最早信号
  • 每次开合记 switches++，并开一个 800ms 的帧窗口；采集时算 switchP95/switchMax
  • 回前台同时监听 visibilitychange 与 window.focus/blur（Alt-Tab 不一定改 document.hidden）；记 hiddenMs / refocus.p95 / refocus.max / flushes
  • panelPx 每次采集读一次宽度；detected=false 表示宿主改版/标记缺失，不猜

P1 · 开合过渡保护（paneSwitchGuardOn，默认开）

只影响 420ms（200ms 过渡 + 220ms 重内容 settle）：

[data-lagfix-pane-switch="1"] [data-panel] {
  transition-duration: 0s !important;
}
[data-lagfix-pane-switch="1"] [data-v4-timeline-message-layer="true"] {
  -webkit-mask-image: none !important;
  mask-image: none !important;
}
  • 开合时把 flex 动画变成一次跳变，避免 12 帧连续重排
  • positionBadge() 顶部先 early-return：不能再让 surfaceRO 在动画中间每帧跑 elementsFromPoint() 强制布局；角标位置最多旧 0.4 秒
  • 420ms 后移除属性，宿主下一轮开合恢复原过渡；关开关立即移除

P2 · 面板常开期保护（paneHoldOn，默认开）

pane.open=true 期间给 documentElement 加 data-lagfix-pane-open="1"：消息层 mask 关闭；effectiveThrottleMs 至少 300ms；角标定位降到 ≤1/1.8s。面板关闭立即移除属性并恢复原规则。

  • 对准截图 B“面板常开、0 次重绘仍有 147ms 帧”的绘制/合成成本
  • mask 只在面板打开期间关，面板关闭后恢复；不是永久关闭
  • 只延迟重绘，不拦 Agent 收流、消息落盘、工具执行

P3 · 回前台保护（refocusGuardOn，默认开）

检测到 hidden→visible 或 blur→focus 后：把待补发的后台通知合并到一个 120ms 定时器（不再同步遍历全部 flusher）；700ms 内通知窗口至少 400ms；前 300ms 不定位角标。

  • 先让窗口完成恢复/首帧，再补 React 状态，避免同一拍多次 commit
  • 只延迟插件挂起的通知；宿主自己的回前台重绘不被拦截
  • window.focus 首次加载也会触发，必须有 lastBlurAt 去重

不做什么

  • 不隐藏、不折叠、不卸载对话或预览内容
  • 不改 loadOlder/补页/返回值，不写 store，不碰 db.sqlite
  • 不拦截或替换宿主的 ResizeObserver，不开 CDP
  • 不把 content-visibility 加到 turn wrapper（virtualizer 要测高）
  • 不在面板关闭时关 mask；P2 只在面板打开期间关

payload 新增 pane 与 refocus

pane: {
  detected: true,          // false = 宿主标记缺失，不猜
  open: true,
  panelPx: 720,
  switches: 3,
  switchP95: 84,           // 最近一次开合后 800ms 的帧 P95
  switchMax: 190,
  guardHits: 3             // P1 实际生效次数
},
refocus: {
  hiddenMs: 8200,          // 上次后台时长；只用时长，不记内容
  sinceVisibleMs: 240,
  p95: 96,                 // 回前台后 800ms 内的帧 P95
  max: 210,
  flushes: 2,              // 合并补发的 flusher 数
  guardHits: 1
}
  • paneDiagOn=false、暂停、dead：pane/refocus=null，与其他诊断字段同口径
  • 只记布尔、宽度、时长、计数与帧统计；不记面板内容、标题、HTML、消息 id
  • 报告新增“侧栏开合”与“回前台”两段：open/closed 分组的帧 P95 中位数、长任务中位数、DOM 中位数；回前台按 hiddenMs 分桶，打印最近一次 refocus.p95/max

同一会话、同一份 HTML、同样开合 5 次、Alt-Tab 5 次；一次只改一个变量。

轮次设置看什么通过线

验收目标：开合 switchP95 ≤80ms（当前 160–294ms）；面板常开 frameP95 中位数 ≤80ms（截图 B 为 147ms）；回前台 800ms 内 refocus.p95 ≤80ms、max ≤250ms，状态 150ms 内追上。任一段达不到就关掉对应开关，只保留有效项；三段都不达标就只保留 P0，不把“观测到尖峰”写成“已改善”。

06 · 已知边界与风险

先说清做不到什么，避免下一版又变成“看起来修了”。

三段各管一段，不保证全治

P1 管开合 420ms，P2 管面板常开期，P3 管回前台 700ms；如果卡顿来自预览 HTML 自身的持续绘制，或者宿主侧的其它长任务，这三段仍可能不够。那属于 O4/预览侧方案，v0.3.3 不把它算进验收。

依赖宿主三个标记

[data-workspace-side-frame="true"]、aria-hidden、[data-panel] 和 transition-[flex-grow] 任一改动，检测会降级为 detected=false 或不再触发保护；报告会提示，不静默假装生效。

P1 会让开合动画消失

P1 生效时面板是瞬开/瞬收，不再有 200ms 的滑动感。这是用视觉换主线程；不喜欢可以只关 P1，P0/P2/P3 仍可用。

P2 有视觉与刷新代价

面板常开期间消息层不再做渐变遮罩，聊天文字最多晚 300ms 刷新；Agent 收流、工具执行、消息落盘都不受影响。若觉得“字变迟”或遮罩不能少，关 P2 即可。

P3 只延迟插件的补发

回前台后最多 120ms 才补发挂起的通知，状态可能比宿主晚一拍；宿主自己的首帧重绘不被拦截。Alt-Tab 首次回到窗口时 window.focus 也会触发，靠 lastBlurAt 去重，不会把普通点击当回前台。

不保证所有机器都变快

当前证据来自一台 Windows 机器、一个超长会话和两张用户截图；5.7k DOM 是一个样本，不是所有会话。没有实机 A/B 前，不写“已修复卡顿”。
